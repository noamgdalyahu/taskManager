# Decision log

Why each algorithm and technology was chosen. Feeds the project book and the oral exam.

## 2026-11-12

| Decision | Choice | Why | Alternatives |
|---|---|---|---|
| Compiled language | C# (.NET 9) | Meets the language requirement; user is most comfortable with it; strong tooling for a framework-free core. | Java |
| Second language | None | The compiled language already satisfies the requirement; less to build and explain. | Python optimization service |
| Database | MongoDB | User preference. Book chapter will describe a document model, references, and JSON-schema validation in place of an ERD. To confirm with the supervisor. | PostgreSQL, SQL Server |
| Client | React | User preference; suits Kanban drag and drop and charts. | Razor/MVC, Angular |
| API style | MVC controllers | Larger app; filters, attribute routing and policy authorization map cleanly onto the layered design. | Minimal APIs |
| Test assertions | Plain xUnit asserts | FluentAssertions needs a paid license in recent versions. | FluentAssertions |
| Solution layout | Core / Data / Api (Application folded into Api) | Layer separation required by track 3; Core stays framework-free so it is unit-testable. | Single project |
| Application layer | Folded into Api (`Services/`) | Fewer projects to explain; logic layer is still a separate folder. Repository interfaces moved to Core so Data does not depend on Api. | Separate Application project |

## 2026-11-13

| Decision | Choice | Why | Alternatives |
|---|---|---|---|
| Topological sort | Kahn (in-degree queue) | Same in-degree bookkeeping feeds the CPM forward pass; deterministic order; leftover nodes give the cycle directly. | DFS with colours |
| Cycle reporting | Return `TopologicalSortResult.Cyclic(path)` | A cycle is manager data error, not a crash; the UI needs the concrete cycle to show. | Throw exception |
| Critical path | CPM forward/backward pass, people ignored | Gives the effort lower bound; capacity is handled by assignment. Keeps each algorithm explainable. | Resource-constrained scheduling (NP-hard) |
| Assignment optimiser | Hungarian with capacity slots | Exact polynomial optimum for a given cost matrix; well documented; the slot expansion + balance pricing + infinity constraints are our adaptation. | Min-cost flow (more general, harder to explain), simulated annealing (no optimality guarantee) |
| Balance in Hungarian | Slot priced by prefix load + own estimate, then iterative re-pricing (≤4 rounds, keep best by true objective) | Hungarian needs costs fixed up front but final load depends on the solution, so round 0 uses a proxy (s × average estimate). Re-pricing from the actual received estimates fixes most of the gap. Measured on 300 random sprints: proxy only 78:54 wins vs greedy; + own estimate 85:34; + refinement **90:22** (188 ties). Tests assert the statistical claim, not per-instance dominance. | Min-cost flow with convex costs (exact balance, harder to explain) |
| Baseline | Greedy (critical first, longest first, cheapest member now) | Mirrors how a manager assigns by hand; gives the "improvement" measurement the rubric asks for. | Random |
| Capacity in Hungarian | Soft constraint: every member gets T slots; overload is priced and warned, never silently dropped | Found by a planner test: slot count from capacity ÷ smallest estimate dropped tasks as "no eligible member" when the only member was overloaded. The manager must see the overload, not lose tasks. | Hard cut-off at capacity |
| Planner pipeline | graph → Kahn → CPM → assignment → feasibility checks; cycle short-circuits | A cycle makes order, slack and assignment meaningless; stop early with the concrete cycle. Other warnings are advisory so the manager can still accept and adjust. | Fail on any warning |
| Calendar | `WorkCalendar`, Fri+Sat weekend, 8h/day, configurable | CPM gives hours; deadlines and sprints are dates. One conversion point, Israeli default. | Calendar days |
| Priority score | Weighted sum of four 0..1 components: deadline urgency, criticality (normalised slack), transitive blocking share, in-progress bonus | Normalised components make weights comparable and tunable; transitive dependents reward unblocking chains. Reasons are generated from the same components so the UI explains the rank. | Single key sort (deadline only) |
| Velocity | Moving average of last 3 sprints, hours/working day | Recent sprints predict better than full history; short window reacts to team changes. | Weighted/exponential average |
| Forecast | Linear burndown extrapolation; in-sprint pace preferred over history; capped at +30 working days | Managers already read burndowns this way; explainable; honest about data scarcity. | Monte Carlo, regression |
| Local MongoDB | Native Windows "MongoDB Server" service on 27017 | Already installed and running on the dev machine (not on PATH, which hid it at first). Docker container removed; compose file kept on 27018 as an optional fallback for other machines. | Docker only |
| Request validation | Data Annotations on record constructor parameters + `[ApiController]` auto-400 | Found at smoke test: `[property:]`-targeted attributes on positional records make MVC throw at bind time; attributes must sit on the parameters. | FluentValidation |
| JSON enums | `JsonStringEnumConverter` globally | Clients send and read `"Manager"`, not `1`; self-describing payloads. | Numeric enums |
| Plan storage | `SprintPlan` serialised to one JSON field in `planJobs` | Keeps Core free of BSON attributes; plan is read whole, never queried by field. | BSON class maps for every Core record |
| Persisted value objects | Explicit JSON converters for `Hours`/ids in plan storage | Bug found by the live flow: System.Text.Json uses the implicit parameterless struct ctor for `Hours`, so a stored plan came back with every duration 0 (critical path 0h, wrong critical flags). Covered by `PlanJsonTests` round-trip. | Public parameterless ctors on value objects (would allow invalid state) |
| Observer for task history | `ITaskChangeObserver` + `TaskChangePublisher`; `HistoryRecorder` diffs before/after | One publish point per change; history today, notifications / PR links / live board later without touching `TaskService`. | Hard-coded history writes in each service method |
| Authorization of resources | `ProjectAccess` is the single gate; non-members always get 404, never 403 | Prevents IDOR and id probing across teams; verified live (outsider gets 404 on project, task, job). | Per-controller checks |
| CRUD result type | Shared `OperationResult<T>` with `ErrorKind`; Auth and Planning keep specific result types | Dozen near-identical result records add no information; the specific ones carry distinct error vocabularies. | One result record per operation |
| Accept plan | Writes suggested assignees; skips tasks edited after the job finished | Manager's later manual changes win over a stale suggestion. | Overwrite everything |
| Estimate accuracy | estimate ÷ logged hours × 100 (100 = perfect, <100 = took longer) | Single readable number per sprint and member for the reports page. | Signed variance in hours |
| Manager as assignee | Project members include the manager, so the planner may assign them work | Small teams where the manager also builds; excluded by simply not being a project member. | Role-based exclusion (revisit with supervisor) |
| Api folder layout | `Controllers/<Page>/` with controller, service, contracts, mapping together; sub-folders where a page splits (`SprintPlanning/Sprints` + `Plans`, `Tasks/Comments`, `Tasks/TimeLogs`, `Tasks/Events`) | User request: one folder per website page so everything about a page is in one place. Shared plumbing (`ApiControllerBase`, `OperationResult`, `ProjectAccess`) lives in `Controllers/Shared`; cross-cutting infrastructure stays outside (`Security`, `Jobs`, `Options`, `Infrastructure`). URLs unchanged by the move (verified by rerunning both end-to-end flows). | Layer folders (`Controllers/`, `Services/`, `Contracts/`) |
| Task authorization | `TaskAccess` (task → project → membership) shared by tasks, comments and time logs | Comments and time logs became their own services; one shared gate keeps "task of another team looks like not found" in one place. | Duplicate checks per service |
| Repository ordering | `GetManyAsync` returns results in the requested order | Bug found by a determinism probe: identical planning input gave different plans because Mongo's `$in` order is unstable and tie-breaks follow member order. | Sort inside the planner |
| Test strategy for services | In-memory fakes of every repository + a prebuilt `World` (manager, 2 members, outsider, project, sprint); mutation spot-checks | Real services under test without MongoDB. Breaking the membership check failed 4 tests and breaking the dependency rule failed 2, proving the tests can fail. | Mocking library (Moq) |
| Load behaviour | Bounded `Channel` queue, N workers (default 2), 202 + polling | 40 concurrent requests: all accepted in <100 ms while plans took 1-3 s to compute; 8 workers gave 3.1x speed-up over 1 (sub-linear: database contention). See `docs/performance.md`. | Synchronous planning in the request |
| Restart recovery | On startup, `Queued` jobs are re-queued oldest-first and `Running` jobs are marked `Failed` ("interrupted by restart"); registered before the workers | The queue is in memory but jobs are in the database, so a restart orphaned them. Reproduced live (zero workers, kill, restart): the job went from stuck `Queued` to `Done`. | Re-run everything automatically (could repeat a half-written side effect) |
| Plan comparison | `PlanComparer` scores Manual, Greedy and Hungarian with the same cost function, same critical set; `GET /api/sprints/{id}/plan-comparison`, capped at 400 open tasks | The track needs a measurable improvement over the existing solution; "existing" here is the manager's hand assignment. Manual is shown only if something is assigned; unassigned tasks are counted separately rather than hidden in the objective. | Only Greedy vs Hungarian |
| Tie handling | `Winners` lists every approach within 1e-6 of the best; `Winner` is null on a tie | Found on the seeded demo: a plan produced by the planner tied with Hungarian but was reported as winning because it was listed first. A tie must not be presented as a win. | First in list wins |
| Seed tool | `tools/SprintManager.Seed` writes via the real repositories; `--reset` removes only `@demo.sprintmanager.local` data | Direct writes allow backdated completion dates (a believable burndown and a closed sprint with velocity); HTTP could only stamp "now". Two deliberate manual mistakes in Sprint 2 give the comparison screen something to find. | Seed through the API |
| Client stack | Vite + React + TypeScript 5.9 + MUI + axios + TanStack Query + motion + dnd-kit | User decisions: Vite/React/TS, MUI for components, axios for server calls. TypeScript pinned to 5.9.3 (the template's TypeScript 7 native compiler has no JS API, which openapi-typescript needs). | TypeScript 7 |
| Client file tree | One folder per page; each component in its own folder with its child components nested inside; shared components in `src/common/`; no barrel files | User decision, recorded in `src/client/CLAUDE.md`. | Layer folders (components/, hooks/, pages/) |
| API types | Generated from the server's OpenAPI document (`npm run api:types`), controllers declare `ProducesResponseType<T>` so every DTO is in the schema, enums are strings in the document | Types cannot drift from the C# DTOs. Two bugs found on the way: enums were `number` in the document (the OpenAPI generator reads different JSON options than MVC) and most DTOs were missing (actions returned bare IActionResult). | Hand-written client types |

| Session storage | JWT in localStorage behind an external store read before the first render | HTTP layer needs the token before React effects run (child effects run before parent effects). Trade-off: readable by scripts on the origin, mitigated by no raw HTML and a 60 minute token. | Memory-only token (lost on refresh) |
| Board drag and drop | dnd-kit with 8 px distance threshold, 200 ms touch hold, keyboard sensor, optimistic move with rollback, plus a "Move to" menu on every card | apple-design: hysteresis before a drag, no scroll hijacking, 1:1 tracking with a lifted overlay. ## Sidenav works like Azure DevOps' left navigation

- **Decision:** the sidebar has a project header (initials mark + name, menu to switch project or go to "All projects"), single links (Overview), collapsible groups (Boards, Insights), "Team" pinned at the bottom like Azure's "Project settings", the account menu, and a « / » toggle that folds it to a 64 px icon rail.
- **Why:** Azure lets you move between projects without a detour, hides what you are not using, and keeps your choice. Group and rail state persist in `localStorage` (`sm.nav`), wrapped in try/catch so a blocked store only loses the memory.
- **Collapsed rail:** every icon has a tooltip and an `aria-label`; a group becomes an icon that opens a flyout menu, so nothing is unreachable.
- **Motion:** the width is a spring (interruptible, reduced-motion aware); the phone drawer stays always wide.
- **Verified in a browser:** widths 232 / 64, group toggle, persistence after reload, flyout, project switcher, phone drawer, no console errors.


## Dark mode switch (replaces the short-lived Glass theme)
- **Decision:** a "Dark mode" switch in the account menu, saved in the browser. A Glass theme was tried first and removed at the user's request.
- **How:** colour tokens are CSS variables (`var(--sm-x)`) defined once for light and once for dark in `src/theme/tokens.ts`; an attribute on `<html>` picks the set. MUI gets one theme per appearance, because its palette needs real hex values.
- **Why variables:** about 50 components style themselves from `tokens.color`; with variables none of them has to know which look is on, and adding the switch touched only the places that had hard-coded colours.
- **Checked:** board, dashboard, planning, task page and menus in a real browser in both looks, no console errors.
